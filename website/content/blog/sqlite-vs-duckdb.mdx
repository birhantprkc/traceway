## TL;DR

Same Hetzner CCX13 as [post 1](/blog/sqlite-observability-stack) and [post 2](/blog/break-sqlite-traceway): $16.49/month, 2 dedicated AMD vCPU, 8 GB RAM, 80 GB NVMe. Two builds of the same Traceway binary: the SQLite build post 2 measured, and the DuckDB build, where relational data stays in SQLite and telemetry moves to DuckDB's columnar engine. Same loadgen, same scenarios, same pass/fail rules.

The whole post in one table:

| | SQLite (post 2) | DuckDB (this post) | Change |
|---|---|---|---|
| Metrics writes | 61,712 pts/sec | 254,242 pts/sec | 4x |
| Spans writes | 30,508 spans/sec | 95,737 spans/sec | 3x |
| Logs writes | 4,877 rec/sec | 75,225 rec/sec | 15x |
| Metrics read cliff | 1M rows (3.85 s median) | 100M rows (3.0 s median) | 100x |
| Spans read cliff | 100k rows (2.27 s median) | 10M rows (902 ms median) | 100x |
| Logs read cliff | 100k rows (114 ms median) | 10M rows (85 ms median) | 100x |

A read cliff, throughout this series, is the largest table size at which real dashboard pages still load: the median of three real endpoint probes at or under 5 seconds, none timing out.

<mark>Each signal's read cliff sits exactly two decades further out on DuckDB than on SQLite, at equal or better latency, on identical hardware.</mark> The box also ingested a billion metric points in 52 minutes into 10.8 GB of disk and stayed up, something the SQLite build cannot get within two orders of magnitude of. Logs, the signal post 2 said to keep off SQLite entirely, is DuckDB's biggest win.

One catch before you trust any of it: my first DuckDB numbers were wrong, because the benchmark kept crashing my own backend. That bug, and the fix that made these numbers real, gets its own section.

## What's actually being compared

Post 2 ended promising a ClickHouse comparison, and that post is still coming. This one exists because a question kept getting in front of it: before reaching for a client-server OLAP database, how far does an embedded one go? Traceway ships a DuckDB telemetry backend as an opt-in build, same single binary, same deployment story as the SQLite build, different storage engine under the telemetry tables. If you self-host on one cheap box, these two builds are the actual decision in front of you, and nobody publishes numbers for that decision. So I ran post 2's entire methodology against the DuckDB build and put the results side by side.

Here's the plan. Methodology and its two new pieces first, then the bug that invalidated my first attempt, because half the final numbers changed after the fix. Then writes, all three signals against their SQLite baselines. Then reads, same shape. Then the billion-row run, what queries cost past the cliffs, the fleet math for both builds, and which build I would actually run.

## How I measured

The setup is post 2's, so I'll keep it short: a system under test (SUT) running the Traceway binary and a separate load generator on a private link, both in Hetzner's Nuremberg datacenter, OTLP over gzipped protobuf, uniform-random data in bounded ranges. Traceway built from commit [`14b4aa6e`](https://github.com/tracewayapp/traceway/commit/14b4aa6e175946d40383d938db22cfea8c23c695), Ubuntu 24.04, retention off during the bench.

Two scenarios per signal. The **throughput ramp**: batch-size ramp at fixed rate, then a request-rate ramp at the winning batch (this time with a finer rate ladder, 1 through 25 req/sec, because the interesting cliffs turned out to sit between post 2's coarser steps), then a small-batch high-rate ramp shaped like an SDK fleet. A step passes at under 5% errors and at least 70% of target rate achieved. The **read-probe**: fill the table to 1M, 10M, 100M, 1B, then 5B rows, and at each level load three real dashboard endpoints per signal, with a level passing when the median is at or under 5 s and nothing hits the 6 s timeout. The 5-second bar is generous on purpose and post 2's discussion of that still applies unchanged.

Three things differ from post 2's harness, all disclosed:

1. **The loadgen grew.** Post 2 generated load from a second CCX13, which SQLite's ceilings never stressed. On my first DuckDB spans run, that loadgen box died mid-ramp while the database sat at 0% errors, the traffic generator broke before the thing it was breaking. The loadgen is now a CCX23. The SUT, the box every number describes, is unchanged.
2. **The digestion gate.** DuckDB checkpoints its write-ahead log after ingest stops; probe during that and you measure a busy engine, not a query. The read-probe now polls the backend's deep-health endpoint until the database and WAL file sizes are stable, records the wait per level (5 seconds at every level in the final runs), then probes. SQLite reports no engine gauges and skips the wait, so its post 2 numbers were produced identically.
3. **Only accepted rows count.** The fill counts items confirmed by 2xx responses, not items attempted, which matters once the backend learns to refuse work. Fills still overshoot their targets slightly, so tables report actual row counts.

Caveats. These are single-shot runs, one throughput run and one read ladder per signal. Post 2 promised medians of three reps starting with this post, and I'm walking that back one more time: the fix-and-rerun cycle below consumed the budget, and I'd rather publish single-shot numbers with that admission than sit on them. The key cells reproduced within a few percent across the debugging runs (100M metrics reads landed within 4% across three runs on different days), but the protocol is single-shot. "Passing" still means three named endpoints on freshly written data on an otherwise idle box; read-under-ingest remains future work.

## The bug between me and the numbers

My first DuckDB throughput run posted 77,899 spans/sec, and then the box went silent, the run's JSON ends with `sutDied: true`. The first read-probe was stranger: logs failed its very first level, all three probes timing out at 3M rows, including a trace-ID lookup that matches at most one row. The same table on my laptop answered that lookup in 1 millisecond. A query does not slow six thousand times because of query cost.

The digestion gate made the failure legible: at the wedged levels it polled the health endpoint for ten straight minutes without one answer. Reproducing the fill locally with the backend's own logs showed the sequence. Under a sustained burst of fat log batches, ingest requests slow from milliseconds to 10, then 17 seconds, and then the process dies with no panic, which is the kernel's out-of-memory killer. Docker restarts it, DuckDB replays the write-ahead log on open, and on two slow cores with gigabytes of un-checkpointed WAL that replay runs for minutes, during which every query hangs. On my laptop the process died three times inside one 56-second fill.

The root cause was mine, not DuckDB's: the ingest path had no admission control. Every concurrent request was decompressed and decoded immediately, each holding megabytes of protobuf while it waited on the database. SQLite never surfaced this because its slower insert path errors early under pressure, post 2's logs wall at 5 req/sec was that error path working. DuckDB is fast enough to keep the front door open until memory runs out.

The fix is a gate at the door: a cap on concurrently processed ingest requests, acquired before the body is read, with a short wait and then a 503 plus Retry-After, which SDKs and OTLP collectors answer by retrying. It applies to every backend and shipped in the commit linked above. Against the same killer fill: 16.4M log rows accepted in 100 seconds, 6,188 requests refused cleanly, WAL held at 62 MB, zero restarts. The fill took 100 seconds instead of 56, and that gap is what surviving costs, part of the old speed was acknowledged data that was about to die with the process.

Two of the final numbers moved a lot once the box stopped dying mid-measurement: spans throughput rose 23% (the crash had been hiding the true ceiling between two coarse ramp steps) and logs throughput nearly doubled (the crash had been knocking the ramp down to a smaller batch size). Every number below is from the fixed backend.

## Writes: 4x, 3x, 15x

| Signal | SQLite | DuckDB | Winning shape (DuckDB) | First failing step |
|---|---|---|---|---|
| Metrics | 61,712/sec | **254,242/sec** | batch 16384 × 20 req/sec, p50 3.2 s | 22.5 req/sec, 12.2% errors |
| Spans | 30,508/sec | **95,737/sec** | batch 16384 × 7.5 req/sec, p50 1.2 s | 8.75 req/sec, 9.7% errors |
| Logs | 4,877/sec | **75,225/sec** | batch 16384 × 5 req/sec, p50 3.0 s | 5.625 req/sec, 11.4% errors |

Three things in this table deserve prose. First, the failure modes match now: every "first failing step" is clean 503 rejection from the admission gate, the container finished all three runs with zero restarts, which is the same graceful-cliff behavior SQLite showed in post 2, and which DuckDB only exhibits because of the fix above.

Second, logs. Post 2's starkest result was logs writing at 4,877/sec with a wall at 5 req/sec so sharp that 1.5x more requests took the error rate from 0% to 98%. The DuckDB build writes logs at 15 times that rate, and the wall became a slope of refusals. The signal with the lowest SQLite ceiling and the highest real-world volume is exactly the one the columnar engine helps most.

Third, the SDK-fleet shape, which post 2 could only measure on SQLite: thousands of small batches per second rather than a few fat ones. DuckDB sustains 53,091 metric points/sec, 36,577 spans/sec, and 30,442 log records/sec at batch 100. My first attempts never produced these numbers at all, the pre-fix backend always died before phase 3 ran.

## Reads: every cliff, two decades later

| Rows (actual) | Metrics | Spans | Logs |
|---|---|---|---|
| ~1M | 146 ms | 139 ms | 27 ms |
| ~10M | 382 ms | **902 ms** | **85 ms** |
| ~100M | **3.0 s, passes** | over 60 s, fails | fails unevenly: body search 3.5 s, trace-id 2 ms, severity filter over 60 s |
| ~1B | fill succeeds, queries over 60 s | not reached | not reached |

Each cell is the median of three real endpoint probes after fill and digestion; bold marks each signal's last passing level. For comparison at a glance: SQLite's last passing levels were 1M, 100k, and 100k. Same endpoints, same thresholds, one hundred times the rows.

Metrics reads scale almost politely: 146 ms at 1M, 382 ms at 10M, 3.0 s at 100M. A hundred times the rows costs twenty times the latency, the scan gets cheaper per row as the table grows. The level SQLite barely passed sits two decades below the level DuckDB passes with the same margin.

![Per-endpoint read latency vs metric_points table size on log-log axes. All three probes sit under 250 ms at 1M rows, under 700 ms at 10M, and between 2.5 and 5 s at 100M, still under the threshold](/blog/sqlite-vs-duckdb/chart-readprobe-metrics.webp)

Spans pay for their percentiles, same as they did on SQLite, just later. The two aggregation-heavy pages, P50/P95/P99 grouped by route and the stacked latency chart, cost 902 ms at 10M rows and blow past a full minute at 100M. Post 2 watched the same two pages die between 100k and 1M.

![Per-endpoint read latency vs spans table size on log-log axes. The two percentile-aggregation probes track from under 200 ms at 1M to about 900 ms at 10M, then exceed the timeout at 100M](/blog/sqlite-vs-duckdb/chart-readprobe-spans.webp)

Logs repeat post 2's most interesting pattern one decade up. At their passing levels they're the fastest dashboard of the three (85 ms median at 10M), and their failure at 100M is uneven in the same way SQLite's was at 1M: the trace-ID lookup still answers in 2 ms, the body search in 3.5 s, and only the severity filter, which matches and ranks a large slice of 100M rows, dies. The pages an on-call actually opens mid-incident, find this trace, search this error, remain usable at 100M rows; the full-table scan does not. Retention policy should still follow that split. The split just moved 100x.

![Per-endpoint read latency vs log_records table size on log-log axes. The trace-id lookup stays at 2 ms across every level, the body search holds under 100 ms to 10M and reaches 3.5 s at 100M, and the severity filter crosses the threshold at 100M](/blog/sqlite-vs-duckdb/chart-readprobe-logs.webp)

## A billion rows on an 80 GB disk

The top of the metrics ladder deserves its own numbers, because nothing in posts 1 or 2 gets near it. The fill accepted 1,001,472,000 metric points in 52 minutes, a sustained 320k points/sec with the gate shedding the excess, into **10.8 GB on disk**, about 10.8 bytes per point after columnar compression. The box stayed up, health checks answered throughout, and post-fill digestion took 5 seconds. On every pre-fix attempt this level ended with the container OOM-killed; on the fixed backend a billion rows is just a big table.

A big table you cannot look at: all three dashboard queries ran past 60 seconds at 1B, so the level fails, and 5B was never attempted since the ladder stops at the first failure. I left it that way on purpose. A 5B fill would prove the disk holds 54 GB of points, and I already know nothing could read them. The practical summary of the ladder's top: this box can store a billion metric points, and it can show you a hundred million of them.

## How slow is slow past the cliff

Post 2 could only say "it timed out" about anything past a cliff. This time I reran the entire ladder with a 60-second probe threshold to put real durations on the failing cells, and the durations barely exist: metrics at 1B, still running at 61 s. Spans aggregations at 100M, still running at 61 s. The logs severity filter at 100M, still running at 61 s while the body search finished in 3.2 s beside it.

So the cliffs are not slopes on either database. Queries go from 3 seconds to more than a minute across one decade of rows, the signature of an aggregation outgrowing the 4 GB memory budget and spilling. There is no slow-but-usable band above a cliff to plan around, which post 2 found on SQLite at one hundredth the scale, and which is why I keep publishing cliffs instead of curves.

The 60-second run also caught a smaller flaw for the fix list: a cancelled dashboard query does not promptly release its read-pool connection, so after the two spans aggregations timed out, a 3 ms exceptions query queued behind them for 52 seconds. It affected no passing number, and it goes on the same list the admission gate came from.

## What fits comfortably, on each build

Post 2's small-fleet shape, ten backends emitting 50 spans/sec, 200 log records/sec, and 10 metric points/sec each, held against both builds:

| | SQLite envelope used | DuckDB envelope used |
|---|---|---|
| Spans (500/sec) | 1.7% | 0.5% |
| Logs (2,000/sec) | **40%** | 2.7% |
| Metrics (100/sec) | 0.2% | 0.04% |

Writes were already a non-issue on SQLite for everything except logs, and on DuckDB they stop being a conversation entirely. Retention is still the real knob, with new units. At this fleet's rates, logs reach their last passing read level (10M rows) in about 85 minutes and the failing level in about 14 hours; spans reach 10M in 5.5 hours; metrics reach 100M in 11 days. On SQLite, post 2 measured the logs window at 50 seconds. An incident-sized working set, hours of spans and logs, days of metrics, fits on the right side of every DuckDB cliff with an ordinary retention job, which is the thing the SQLite build could not offer.

## What I deliberately didn't measure

- **Read under concurrent write.** Fill, digest, settle, probe. Stricter isolation than post 2, and still not what a dashboard experiences at 3 PM. Top of the future-work list.
- **Mixed-signal load.** Each signal had the box to itself; a real deployment writes all three at once and these ceilings do not simply add.
- **Result correctness.** I timed responses, I did not diff their contents.
- **Variance.** Single-shot, as admitted in the methodology, with the median-of-three protocol still owed.
- **Tuning.** Stock config: 4 GB DuckDB memory cap, 256 MB checkpoint threshold, no schema or query changes. The 1B read failure smells like it wants a memory-budget experiment, and that is a deliberate cliffhanger.
- **Durability over weeks.** A 52-minute billion-row fill says nothing about month three on the same disk.

## What surprised me

I expected the reads to win, that's what columnar storage is for. I did not expect all three cliffs to land exactly two decades up, a symmetry I would have dismissed as marketing if I hadn't produced it from the raw JSON myself. And I did not expect the database to be the easy part: every wrong-looking number in six days of benchmarking, a 1 ms lookup timing out, a ten-minute blackout, a dashboard "cliff" at 3M rows that wasn't real, traced to my own ingest path, not the engine. DuckDB, whenever my code got out of its way, was boring in the best way a database can be boring.

The other surprise was logs, again. Post 2's verdict was "keep logs off SQLite," and logs turned out to be the strongest single argument for the DuckDB build: 15x on writes, 100x on the read cliff, with the incident-workflow pages still answering at 100M rows.

## The verdict

Which build should you run on the cheap box? After these numbers, the DuckDB build, for almost everyone self-hosting on a single machine. Every signal writes faster than a small fleet emits, the dashboards survive row counts the SQLite build cannot approach, logs go from "keep them off this database" to the best result in the dataset, and a billion metric points cost 10.8 GB of disk.

The SQLite build keeps two honest advantages. It compiles anywhere Go does, while the DuckDB build needs CGO and glibc, so its container image is Debian rather than Alpine. And its storage engine does all its work inline, no deferred checkpoints, no digestion window, no 503s under burst, the trade being that its ceilings sit 4x to 100x lower. If your telemetry volume lives comfortably under post 2's numbers, the SQLite build remains the simplest thing that works. The moment logs matter or retention beyond an hour matters, the comparison stops being close.

And the honest asterisk on the whole table: these numbers exist because the benchmark first found a crash bug in my ingest path and I fixed it. If you run the DuckDB build, run a version with the admission gate. The engine was never the problem; the code in front of it was.
